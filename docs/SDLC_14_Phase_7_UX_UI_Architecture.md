# Phase 7: UX / UI Architecture

This phase defines the frontend design philosophy for HRT Systems, built on React / Next.js. The defining mandate from the Master Context is to maintain a **"Xero-simple on the surface, enterprise-grade underneath"** positioning, while designing around *business events* rather than accounting screens.

## 1. The "Iceberg" Design Philosophy
The fundamental UI challenge is exposing the power of an enterprise accounting kernel without causing "Soul-Crushing Friction" for small businesses.

*   **Role-Based Progressive Disclosure:** An operational user (e.g., a Sales Rep or Warehouse Worker) should never see a debit, credit, or a GL account. They see operational forms (e.g., "Ship Order" or "Create Quote").
*   **The Accountant's Toggle:** Finance users have access to an "Accounting View" toggle on operational screens, instantly revealing the underlying `Accounting Event`, exact GL impacts, and dimensions generated by the action.

## 2. Business-Event Driven Interfaces
The UI does not force users to understand accounting mechanics. 
*   **Action-Oriented Buttons:** Instead of a button saying "Post Accrual Journal," the UI says "Acknowledge Goods Received." The React frontend passes this payload to the FastAPI backend, which translates the *Business Event* into the complex GRNI *Accounting Event*.
*   **No "Orphaned" Journals:** While accountants can post manual journals, the UI strongly funnels users toward operational workflows (Invoices, Receipts, Bank Matches) to ensure the subledgers remain pristine.

## 3. The Universal Workflow Component
As defined in the Master Context, almost all entities flow through: `CREATE → VALIDATE → ENRICH → APPROVE → COMMIT`.

*   **Standardized UI Shell:** Instead of building 50 different screens from scratch, the React frontend uses a Universal Workflow Shell for AP Bills, AR Invoices, and Expense Claims.
*   **The "Enrichment" Sidebar:** When an AP Bill is scanned via OCR (Create & Validate), the UI presents an "Enrichment" sidebar. This is where the user seamlessly tags the dynamic EAV Dimensions (e.g., assigning the bill to a specific `Project` or `Department`) before hitting Approve.

## 4. Handling Dynamic Dimensions Elegantly
Because HRT Systems uses customizable, dynamic dimensions rather than fixed columns, the UI must handle data entry gracefully.

*   **Smart Tagging:** Dimension entry looks like modern "tagging" (e.g., Jira or Asana) rather than rigid, scary dropdown matrices.
*   **Inheritance:** If a user tags an Invoice Header to `Project Alpha`, the UI visually confirms that all line items will inherit this dimension, removing the friction of repetitive data entry.

## 5. Technical Frontend Architecture (React / Next.js)
*   **Optimistic UI Rendering:** To achieve "Zero Friction," the React frontend uses optimistic updates. When a user matches a bank transaction, the UI instantly marks it as cleared while the Temporal integration confidently processes the match in the background.
*   **Data Fetching:** Utilizing React Query / SWR for heavy data tables (like the GL or AR Aging) to ensure pagination, caching, and instant search capabilities without freezing the browser.
